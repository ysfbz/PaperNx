## 1. Findings, ranked by urgency

All line references are to the audited SHA unless otherwise stated. Follow symbols rather than line numbers after future edits.

### P0-A — Warm disk cache becomes cold after upgrade (new regression, highest-priority hypothesis)

- [Current CoverRepository::cacheKey, src/cover_repository.cpp:102–121](../src/cover_repository.cpp#L102-L121) hashes path, ID, bytes, modified and comic decoder suffix. It now uses book.bytes and book.modified directly when bytes is nonzero. It only restats when bytes == 0; mtime fallback is nested in that branch.
- [Previous cacheKey](https://github.com/ysfbz/PaperNx/blob/3d39efb0a44d6c62a9b1977fabfb220297ae7537/src/cover_repository.cpp#L102-L118) restatted the actual file and used last_write_time().time_since_epoch().count(), not the stored scan timestamp.
- [src/fs_adapter.cpp:88–90, 330–336](../src/fs_adapter.cpp#L88-L90) and [src/library_index.cpp:99–107,432–443](../src/library_index.cpp#L432-L443) populate Book.modified using stat seconds or a seconds-converted filesystem timestamp. The previous raw file-clock tick/epoch representation can differ from this value even when artwork and file contents are unchanged. This is not merely a faster implementation of the same cache key.
- No legacy-key lookup, migration, key-version discriminator or compatibility alias is present in read(). Existing PNXC0001 files can remain on disk under unreachable names, occupying the enlarged 192 MiB/2048-entry budget while the same original covers are decoded again. Exact hit losses on Switch must be verified using the pinned devkitA64 toolchain and an actual pre-upgrade cache.
- Same-size source changes may now also reuse stale keys when the Book snapshot is not refreshed. Existing tests/cover_repository_tests.cpp:16–58 construct Book with default bytes == 0, exercising the fallback instead of the production populated-Book branch.

**Fix:** Define one canonical versioned cover fingerprint (normalized safe source path/ID, verified size, explicitly documented timestamp unit/epoch plus known/unknown status, decoder algorithm version). Keep documentId and reading data unchanged. Support validated legacy raw-tick keys and current v0.9.4 snapshot keys using bounded on-demand migration, not a full cache wipe or global source rehash. Read previous PNXC0001 payloads only after header/key/checksum and source identity validation; rewrite or copy under new key atomically on a background maintenance path. Unknown or unreliable mtime must not silently claim strong cache validity; use an inexpensive safe verification policy and measured fallback. A full file hash per cover is prohibited on the interactive path. Invalidate RAM, disk and negative cache on verified source fingerprint change. Test old->new upgrade with actual cache populated before upgrade, no regeneration for unchanged supported artwork when a verified legacy key exists, and same-size modified files with nonzero Book.bytes.

### P0-B — Prefetch is FIFO, not viewport priority (new regression)

[src/main.cpp:3075–3101,4351–4396](../src/main.cpp#L4365-L4396):
- renderLibraryScreen calls prioritizeCovers before grid/list drawing. It computes a window starting one row above the viewport and ending beyond the visible rows; visibleRows already includes +2, followed by another +2 in preEnd.
- It enqueues from preStart to preEnd in ascending index order. getOrRenderThumbnail normally pushes to the FIFO tail; only lastLibraryBookId gets push_front. No visible-vs-speculative priority, no actual scroll-direction sorting and no promotion of an existing queued prefetch request when it becomes visible.
- The 48 prefetch threshold / 64 total pending slots include queued, decoding and upload-ready work. Off-screen jobs can obstruct visible covers. Completion upload also consumes FIFO order (main.cpp:1045–1104), so speculative results can delay actual visible images even after decoding.
- queuedThumbIds_.size() at line 4391 is read outside queueMutex_, while worker failure/no-cover paths mutate the set under that mutex. This is a real C++ data race, not just a tuning issue. Current code also removes queued work outside the wanted window but allows already-running obsolete work to finish; completed results outside the window are discarded even if still useful in a bounded CPU cache.

**Fix:** Shared scheduler with strict current-viewport (focused/visible first), adjacent directional prefetch, idle/background lanes, token/fingerprint identity, promotion and deduplication. Compute exact rect intersection from the shared LibraryLayout/scrollbar geometry; avoid treating partially/fully offscreen speculative rows as visible. Reserve slots/bytes for visible requests; never allow speculative jobs to occupy all capacity. Make viewport changes replace/reprioritize pending low-priority work, not cancel every valid result. Keep a small bounded decoded RGB cache for recently left viewport, upload visible results first, pin currently visible GPU textures, stop redundant work on stale fingerprints, and protect all shared containers. Keep SDL texture operations on renderer thread.

### P0-C — Async disk persistence still blocks cover reads (new regression)

[src/main.cpp:850–945,976–994](../src/main.cpp#L850-L945):
- persistMetaWorkerLoop holds coverRepoMutex_ across CoverRepository::write(); thumbWorkerLoop needs that same mutex across read() and again for updateCoverCounters().
- [src/cover_repository.cpp:227–264](../src/cover_repository.cpp#L227-L264) write performs SD file open/write/flush/close, reads the temporary file back for verification and renames/removes entries while the caller holds the repository lock. FAT/SD write stalls therefore block the next visible cache read and can serialize the new two-worker pipeline. Publishing decoded RGB before persistence helps the current cover but does not remove contention for the next one.
- Persistence holds a duplicate RGB buffer per item, up to 256 jobs (rough upper bound 23 MiB RGB alone at 150x210x3, excluding object/decoder memory). Jobs are silently dropped at the cap; pending writes are not drained when workerRunning becomes false. A rapidly closed app can therefore have fewer warm-cache entries next launch. Clear/rescan needs an epoch to reject old pending writes. Disk writes are processed even while coversPaused_ is true.
- Cache startup [initialize:144–185](../src/cover_repository.cpp#L144-L185) performs two directory traversals, plus entry stat/size and recovery. Growing 512->2048 entries can increase startup time; initial thumbWorker updateCoverCounters() calls stats(), which initializes the repository before first cache lookup. Incremental byte total is O(1), not the whole disk cache: eviction still uses min_element over a map.

**Fix:** Make cache lookup fast-path independent of full inventory scanning and slow persistence, with one authority for cache index mutation and short critical sections. Use safe per-key immutable published files or a priority-controlled I/O service; coordinate read/write/clear/eviction without holding global lock across slow file operations. Preserve FAT atomic recovery, checksum, path/symlink containment; do not just remove locks or verification. Defer recovery/full accounting/eviction to bounded background work; maintain O(1) bytes and true efficient LRU if measured necessary. Rate-limit writes during viewport fill and reader access, use bounded shared RGB buffer ownership, coalesce jobs by fingerprint, keep byte budgets and counters for dropped jobs. Persist useful entries before ordinary shutdown within a measured bounded budget; do not block exit indefinitely. Clear epoch must prevent stale writes from recreating cleared cache. Restore safeRoot/owned-file checks where bypassed by new code; corrupt existing entries must not be accepted solely because regular(final) returns true.

### P0-D — Metadata worker competes with decode and can stall (new concurrency risk)

[src/main.cpp:786–817,850–895,912–918,952–964](../src/main.cpp#L786-L817):
- Startup scheduleMetadataIndex runs before visibleBooks_ is built; it queues the full library. Later it queues all filtered visibleBooks_ (not the actual viewport) then all books.
- persist worker considers thumbQueue_.empty() sufficient to start expensive metadata work. The queue can be empty while a visible thumbnail is actively opening/decoding or waiting to upload. Two workers can open the same source concurrently because collectBookMetadata checks metadataLedger under lock but does not atomically reserve a fingerprint before open.
- CV predicate combines persistMutex_ and queueMutex_ state; no explicit persist notification on the final thumbnail dequeue/cache-hit, no-cover/failure completion or reader resume (resume notifies queueCv_ only). Metadata may remain sleeping when it becomes eligible. Cross-lock predicate mutation/notification needs deterministic tests; do not claim a deadlock without reproduction.
- Metadata apply before texture upload may sort/group the entire large library repeatedly, changing viewport and invalidating useful work, including during right-stick scrolling which has no active finger.

**Fix:** Delay full-library metadata scan until visible covers settle; use explicit queued/in-flight/ready visible state and one atomic single-flight reservation per fingerprint; share extracted metadata with cover decode. Throttle metadata under reader/scroll demand; batch UI application at safe idle points, preserve anchor and book focus. Use a consistent mutex/CV predicate or scheduler event model, notify on all state transitions, deterministic shutdown and cancellation. Maintain metadata correctness, user edits and catalog persistence without starvation. Instrument concurrent memory and disk contention on Switch applet/full-memory modes; do not blindly add threads.

### P1-E — Slow decode path remains unchanged

[src/mupdf_bridge.c:138–204,475–519,872–903](../src/mupdf_bridge.c#L138-L204):
- Every cold thumbnail opens a normal document via px_document_open_limited; EPUB calls fz_layout_document and counts pages before extracting/displaying the explicit cover. Cover data already comes from EPUB package metadata, so full pagination often provides no benefit to an embedded-cover thumbnail.
- PDF/CBZ/CBR still take general document/comic opening paths; solid RAR can be expensive. This was present before the regression but cache misses and extra speculative work amplify it. Heavy head-of-line work still exists with one decode worker.
- Missing EPUB cover is inferred from a null buffer; load_epub_extras catches failures and can set cover to NULL. Distinguish truly absent artwork from read/size/decode errors before negative caching.

**Fix:** Build bounded cover-only extraction paths where supported: EPUB container/OPF manifest -> validated cover image without reflow (support EPUB2/3 metadata and existing fallback cases); PDF first-page rendering at thumbnail resolution without unrelated layout; CBZ/CBR cover/first readable image with bounded archive inspection and existing secure RAR4/RAR5/solid fallback. Preserve path traversal, ZIP bomb, malformed input and memory protections, and original artwork/aspect ratio. Use existing MuPDF behavior as fallback for unsupported layouts, not unsafe custom parsing. Separate open, metadata, archive and raster timings. Only consider limited extra decode concurrency after measurements with independent contexts and strict memory budgets.

### P1-F — Retry, scan generation and texture correctness

- [main.cpp:759–780,3075–3101](../src/main.cpp#L759-L780): 5s retry improves on old 30s but only checked during getOrRenderThumbnail/render; failure and no-cover completion do not independently schedule a redraw or due retry. Event loop pending work ends when active requests clear; idle screen may not retry until next render. NoEmbeddedCover is checked by ID before fingerprint ledger; a changed same-ID source can retain stale negative state.
- [library_scan.inc:109,175–192](../src/library_scan.inc#L175-L192) invalidates active tokens by scan generation, but old queue entries can remain. Worker dequeues Book and looks up current token by ID, so an old queued Book may be associated with a fresh request. Validate immutable job identity rather than fetching token at dequeue. A non-changing scan should preserve usable artwork; changed source must invalidate all relevant cache layers.
- [main.cpp:1083–1091](../src/main.cpp#L1083-L1091) ignores the bool return from thumbCache_.put(). [PageCache::put](../src/page_cache.cpp#L78-L109) can reject/destroy a texture, yet caller reports upload success. RAM cache key is ID only, not fingerprint, and visible textures are not passed as protected keys.
- Metadata/cover result publishing needs an explicit wake/dirty signal and deterministic retry timer. Current 8ms poll while pending is an improvement but not a substitute for completion/retry events; check no-cover/error state transitions, retry backoff and renderer reset.

**Fix:** One explicit job state machine: requested -> queued -> in-flight -> RGB-ready -> texture-ready or absent/retryable/permanent error; each transition resolves counters exactly once, token+fingerprint+generation travel with job. No stale results or cache resurrection. Fingerprint-aware RAM and negative cache; bounded LRU instead of clearing all negative entries at capacity; retry timer independent of manual input. Check PageCache::put result before marking loaded. Protect visible textures, retain across unchanged scan, no false success. Preserve pause/resume/shutdown and clear atomicity.

### P2-G — Editorial placeholders may add renderer overhead (measure, do not undo visuals)

[include/papernx/cover_design.hpp](../include/papernx/cover_design.hpp) now has 14 palettes and multiple templates, more primitive draws and wrapped text. [src/typography.cpp:155–242](../src/typography.cpp#L155-L242) has a bounded shared text texture cache (256 entries plus bytes budget); rapidly scrolling through unique titles may churn it. This is a plausible secondary cost, not established as the primary regression. Keep modern placeholders, profile per-frame raster/draw cost, and use a small separately bounded cached layout/texture strategy keyed by title/author/theme/size only if measured useful. Do not replace valid originals with generated covers or reduce artwork quality to achieve a benchmark.

## 2. Why the old benchmark missed this

- [tests/cover_app_benchmark.cpp:82–108](../tests/cover_app_benchmark.cpp#L82-L108) renders startup, waits for library scan, then waits for all metadata to finish BEFORE starting firstViewportReadyMs. It therefore excludes real startup contention and may allow covers to finish while the timer is not running.
- waitForCovers at lines 33–45 checks empty active requests/completed queue, not that all actual visible books with valid artwork are textured and drawn. Failed/no-cover requests and queue-policy artifacts can hide bad fill rates. visibleTextures counts starting at index zero; visibleRows assumes list geometry. Grid and arbitrary scroll anchors are not tested by this metric.
- CoverTelemetry epoch is all outstanding requests including speculative work; firstVisibleMs records an uploaded texture, not necessarily a visible rendered cover. Fill denominator changes on unavailable results. The last bounded 256 samples do not describe every startup/scroll frame. New code adds more prefetch, changing metric semantics between versions.
- tests/run_cover_app_benchmark.py runs cold then warm on the same app root, but the app benchmark clears cache toward the end of each run and does not model old-release->new-release cache migration. A warm run may begin with only a small repopulated viewport. It reports distributions, but no explicit baseline improvement gate. Software SDL renderer and repeated synthetic CBR content are not physical Switch SD evidence.
- Existing repository tests cover bytes==0, not realistic populated Book timestamps; they do not prove production migration or cache invalidation behavior.

These limitations explain why PASS and a stable release label do not establish real cover speed. The release notes' claim of faster covers is not sufficient evidence.

Required deterministic invariants:

- Metadata cannot compete with an outstanding visible job unless a measured bounded policy proves safe; same fingerprint has at most one metadata extraction in flight, all eligible work eventually executes.
