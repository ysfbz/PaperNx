# PaperNX self-updater

The updater checks releases only from `ysfbz/PaperNx` and accepts only the exact `PaperNX.nro` asset with a matching SHA-256 and valid PaperNX NRO/NACP identity and version. TLS peer and host verification stay enabled. A missing or unreadable RomFS trust bundle is an error; the updater never disables verification or uses an unverified fallback.

The configured GitHub releases endpoint requests `per_page=30`; the bounded parser accepts up to 30 release objects and rejects larger responses. `draft` and `prerelease`, when present, must be JSON booleans. A schema/type violation fails the response closed rather than treating a mistyped draft flag as `false`.

For each release, the parser retains at most the exact `PaperNX.nro` and `PaperNX.nro.sha256` assets used by installation. Other release assets are parsed for validity and discarded; a duplicate install asset is made unusable. This bounds retained asset metadata without weakening response-size, JSON-node, origin, digest or NRO validation.

Automatic launch checks default to off and are stored in app settings. A manual check remains available. When enabled, the launch check starts only after the first rendered frame and performs network work on the updater worker. Release notes and the NRO are shown before download; the user must choose Update. Once verified, the UI shows the staged file path and manual replacement steps. There is no in-app restart/install action. Download cancellation removes the partial `.part` file. The updater stages only files adjacent to `PaperNX.nro`; progress, catalog, settings, books and Reading Journal are not written by the update flow.

Cancellation stays active through transfer, NRO/hash validation and staging. A cancelled or failed download removes its partial file and only the inactive candidate slot; the previously selected verified candidate stays intact. Candidate publication writes its payload and metadata into separate slot-specific names. `Ready` is published only after both are saved and revalidated. The terminal `Ready` transition and `cancel()` are serialized by the status mutex, so a cancel after `Ready` does not retroactively undo a completed package.

## CA trust bundle

`romfs/cacert.pem` is curl's PEM conversion of Mozilla's public root store, downloaded from [curl.se/ca/cacert.pem](https://curl.se/ca/cacert.pem). The source documents that the converted bundle retains Mozilla's **MPL-2.0** license: [CA extract and license details](https://curl.se/docs/caextract.html). The bundled revision was updated by Mozilla on **2026-10-20** and contains **118 certificates**; its SHA-256 is `796f1389bfea13c0ed78f663b765baaff54a508e5483786bd6ece73c5e3e3cbe` and its size is **200,116 bytes**. `scripts/license-notices/curl-ca-bundle.md` preserves this attribution in generated license archives.

`make all` parses the PEM before compiling, and `scripts/verify_artifacts.py` confirms the same file is embedded in the NRO RomFS. The current trust set is intentionally a Mozilla general-purpose bundle; update it from curl's maintained extract and revise this checksum/size record when refreshing it. The native Switch build produced an AArch64 ELF and NRO containing this exact 200,116-byte source bundle. The NRO's RomFS is 1,962,916 bytes; that includes fonts and other RomFS entries, so it is not a before/after size comparison.

## Verified download and manual installation

The updater never replaces or renames the running `PaperNX.nro`. It downloads to the adjacent `.part` file and validates the TLS response, SHA-256, NRO structure, PaperNX NACP identity, version and byte count before publishing a candidate. There are two independent payload/record pairs: the legacy `PaperNX.nro.new` + `.ready` slot and `PaperNX.nro.new.1` + `.ready.1`. New records include the hash, version, byte count, slot number, generation and `Ready` status. The old three-line `.ready` format remains readable as slot 0. On each check, both pairs are validated independently; the highest valid SemVer wins, with slot 0 as the stable tie-break. Missing or corrupt candidates cannot borrow another slot's metadata. Incomplete `.part`, temporary record and unpaired slot files are cleaned on the next check.

The UI names the selected staged file and instructs the user to close PaperNX and use a file manager to replace the canonical NRO. The user should retain a backup of the existing NRO until the replacement has launched successfully. PaperNX does not perform that external replacement or claim an automatic rollback for it. When a newer release is downloaded, only the non-selected slot is replaced, and only after the new `.part` has passed all validations. A write, rename, cancellation or space failure therefore leaves the previously selected candidate available. If a new candidate later fails validation, the remaining valid slot can be selected at the next check.

An unmarked `PaperNX.nro.old` is treated as a user-retained backup: startup leaves it intact, and it does not prevent staging another verified update. Legacy boot markers (`.boot`, `.boot.started`, `.boot.ok`, `.swap`) still block a new download until recovery is resolved. If the canonical NRO is missing with only an `.old` backup and no legacy transaction marker, startup fails closed and directs the user to restore that backup; it does not attempt an unproven external-file-manager rollback.

This selects the verified-manual strategy because PaperNX has not established destination-replacement or power-loss guarantees for the Switch filesystem. The [libnx filesystem API](https://github.com/switchbrew/libnx/blob/master/nx/include/switch/services/fs.h) exposes rename and commit operations, but those declarations alone do not prove an atomic replace contract for the target SD filesystem. An immutable launcher/versioned-payload strategy is also not adopted without a tested chainload and boot contract. The verified-manual flow avoids the application's known FAT rename window because the application does not mutate the canonical executable. It is not a claim that every external file manager performs a power-loss-safe replacement. If the external replacement is interrupted, recovery is manual from the retained backup or another copy of the NRO. The downloader writes only updater-owned adjacent files (`.part`, `.new`, `.ready`, `.ready.tmp`, `.new.1`, `.ready.1`, and `.ready.1.tmp`); it does not write progress, books, settings, catalog or Reading Journal data.

`prepareBoot()` and `confirmBoot()` remain for recovery of transactions created by earlier self-installing builds. For those legacy transactions, startup confirmation still means that PaperNX rendered its first frame, not that every feature passed. If a legacy install left the canonical NRO missing, PaperNX cannot execute its own recovery code; restore `PaperNX.nro.old` to `PaperNX.nro` with another homebrew file manager or from a computer. This legacy recovery path has not been physically tested.

Local HTTPS integration tests exercise valid and invalid certificates, source/asset restrictions, cancellation, truncated bodies, wrong hashes, wrong app identity/version, staging cleanup, tampered pending files, unchanged canonical NRO and legacy startup recovery. These tests run on the desktop host. A real Switch TLS request, file-manager replacement, SD-card interruption and legacy boot recovery have not been exercised on hardware.

At source revision `cb5eb7a` (built with report-only commit `4ba0aa0`), the Switch cross-build and `scripts/verify_artifacts.py --version 0.9.1` passed: libcurl-linked AArch64 ELF, NRO output, and embedded CA equality (118 certs / 200,116 bytes). This verifies compile/link and packaging inputs, not a real Switch HTTPS request or external file-manager recovery.

At source commit `ebf6555`, updater unit and local HTTPS integration tests pass **2/2**. The integration suite includes a 16 MiB transfer cancelled at 100% reported progress, then checks that no partial or staged package remains. This is host evidence; Switch cancellation timing and SD-card interruption remain unverified.

## Staging states (recovery session)
`Checking` → `Available` → `Downloading` → `Verifying` → `Ready` (= downloaded, verified, **staged**; never installed). `Cancelled` and `Error` retain the previous selected candidate in status when one is valid. A restart independently rediscovers and validates both slots. Legacy `.new`/`.ready` installations migrate by read-only validation as slot 0; no user data is moved. Staging refuses to start while legacy `.boot`/`.boot.started`/`.boot.ok`/`.swap` markers exist. Automatic power-loss-tolerant installation is **BLOCKED**: it needs verified HBL chainload to a versioned slot and FAT rename/flush evidence on a real Switch. Slot isolation preserves the prior candidate across application-visible failures; FAT directory persistence under physical power loss is not claimed or hardware-verified.

## Final blocker verification — source `0eaf3b38`

On the final code source, `papernx_self_update_tests` and `papernx_self_update_network_tests` passed in both the full desktop CTest suite (**2/2**) and the full ASan/UBSan CTest suite (**2/2**). Fault injection covers cancellation, disk-full, payload/record rename and fsync failures, invalid SHA/NACP/version, interrupted transfer, and candidate selection. The running `PaperNX.nro` remains unchanged throughout download and staging. The complete native suite and cross-build evidence are recorded in `FinalDevelopmentResult.md` and `docs/V092_FINAL_ACCEPTANCE_MATRIX.md`.

The automatic install decision remains **BLOCKED** for the same evidence gap: HBL `envSetNextLoad()` argv/RomFS/reboot recovery behavior and FAT power-loss replacement behavior have not been proven on a physical Switch.
